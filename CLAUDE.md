# CLAUDE.md

Правила для Claude Code (и других агентов) при работе в этом репозитории.

## Проект

RAG-система поверх личного Obsidian vault. Учебный pet-проект: автор проходит путь PHP/Symfony → AI/GenAI Engineer, каждый слой проекта привязан к этапу обучения. Полный контекст обучения и роадмап — в Obsidian (`ML Learning/Практика — VaultAssistant/index.md`), не здесь.

Текущее состояние слоёв — в [docs/CHANGELOG.md](docs/CHANGELOG.md).

## Документирование решений (ADR)

Когда принимается значимое решение — выбор библиотеки, архитектурный подход, компромисс, отказ от альтернативы — создать файл `docs/decisions/NNNN-краткое-название.md` (следующий номер по порядку) по шаблону:

```markdown
# NNNN — Заголовок

**Статус:** принято — YYYY-MM-DD

## Контекст
Какая проблема решается, какие были варианты.

## Решение
Что конкретно выбрано.

## Обоснование
Почему именно так.

## Последствия
Что это ограничивает/открывает, когда пересматривать.
```

**Что считается значимым решением:** выбор библиотеки/модели, структура данных, которая повлияет на дальнейший код, компромисс с явным недостатком (например, "пока без X, потому что Y"). **Что не считается:** именование переменных, форматирование, тривиальные однострочные правки — для них ADR не нужен.

После создания ADR — добавить одну строку в `docs/CHANGELOG.md` со ссылкой на файл решения. Changelog не должен содержать обоснований — только факт изменения и ссылку.

## Комментарии в коде

Не писать комментарии, объясняющие, что делает код — имена функций/переменных должны говорить сами за себя. Комментарий допустим только когда без него неочевидна причина (не описание): скрытое ограничение, обходной путь для конкретного бага, поведение, которое удивит читающего. Если комментарий описывает "что" — он лишний, это должно быть в ADR (для решений) или просто не нужно (если тривиально).

## Учебный режим

Автор целенаправленно пишет часть кода сам — особенно там, где код напрямую реализует изучаемую ML/математическую концепцию (например, `cosine_similarity`, механику поиска). В таких местах не подставлять готовое решение без явной просьбы — сначала объяснить концепцию и дать написать самому, проверить/поправить после попытки.

Инфраструктурный и вспомогательный код (обвязка, обработка ошибок, установка зависимостей, конфигурация) можно писать сразу — это не учебный момент.
