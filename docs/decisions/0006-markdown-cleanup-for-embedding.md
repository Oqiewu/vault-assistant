# 0006 — Очистка markdown-синтаксиса перед embedding

**Статус:** принято, известное ограничение зафиксировано — 2026-09-13

## Контекст

`Progress Tracker.md` (таблица прогресса Go Learning) показал низкое сходство (`0.453`) с релевантным запросом "на чём я остановился в изучении Go?" — ниже порога, прошедшего в топ-5 (`0.655+`). Причина: markdown-синтаксис (`[[wikilinks]]`, `|` таблиц, эмодзи-иконки статусов) — шум для embedding-модели, обученной на естественном языке.

## Решение

Добавлена `clean_for_embedding()` в `chunk_vault.py` — убирает wikilinks (заменяет на текст ссылки), символы `|`/`#`, известные эмодзи-иконки. Применяется **только** к тексту, который идёт в embedding-модель (`build_index()` в `embed.py`); в промпт LLM (`rag.py`) по-прежнему идёт оригинальный `chunk.text` — markdown не мешает генерации, только поиску.

## Обоснование

Разделение "текст для поиска" и "текст для генерации" — стандартная практика: то, что помогает эмбеддингу, может быть избыточным/вредным для LLM-контекста, и наоборот.

## Известное ограничение (не решено)

Очистка синтаксиса подняла сходство `Progress Tracker.md` лишь до `0.485` — недостаточно, чтобы попасть в топ-5. Корневая причина глубже: табличный контент (короткие статусы `"Тема X: не начато"`) семантически непохож на естественноязыковой вопрос, даже без markdown-шума. Полноценное решение — превращать строки таблиц в предложения перед chunking'ом (например, "Тема 1.1: статус изучено, дата ..."), что требует парсинга структуры таблицы, а не только текстовой очистки.

## Последствия

Отложено до Слоя 5 (Evals) — там нужен систематический способ находить подобные слепые зоны поиска, а не полагаться на ручную проверку одного запроса.
